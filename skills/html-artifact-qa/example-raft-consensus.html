How does Raft consensus work?

TL;DR: Raft keeps a cluster of servers agreeing on a replicated log by electing one leader per term. The leader accepts all writes, replicates them to followers, and commits only after a majority acknowledges. If the leader dies, a new election starts. Raft is designed to be understandable — it avoids the complexity of Paxos by decomposing consensus into three largely-independent sub-problems.
The three sub-problems Raft solves
Sub-problemWhat Raft does
Leader electionUse randomised timeouts to elect exactly one leader per term; re-elect on failure.
Log replicationLeader appends entries and sends AppendEntries RPCs; commits when a majority acknowledges.
SafetyLogs are only committed once a majority hold them; new leaders must contain all committed entries.
Node state machine

Every Raft node is always in one of three states:

  • Follower: passive; replicates entries from the leader; resets its election timer on each heartbeat.
  • Candidate: started an election; requests votes from peers; becomes leader on majority or reverts to follower if it sees a higher term.
  • Leader: sends heartbeats (empty AppendEntries) to maintain authority; accepts client writes; steps down if it sees a higher term.
Leader election — randomised timeouts prevent split votes

Each follower picks a random election timeout (e.g. 150–300 ms). If it receives no heartbeat before the timeout fires, it:

  1. Increments its current term
  2. Votes for itself and sends RequestVote RPCs to all peers
  3. Wins if it receives votes from a majority of the cluster

Why random timeouts? They break ties: with high probability exactly one node fires first, starts an election, and wins before the others even notice. A split vote (two candidates each getting some votes) triggers a new term after another random timeout — convergence is fast in practice.

# Safety invariant (§5.2)
# A node grants a vote only if:
#   1. candidate.term >= self.current_term
#   2. candidate.log is at least as up-to-date as our own log
#      (compare last log (term, index); higher term wins; same term = longer log wins)
Log replication — commit requires majority acknowledgement

The leader commits once it sees ACKs from a majority (itself + 1 follower in a 3-node cluster). It then responds to the client and piggybacks the updated commitIndex in the next heartbeat so followers apply the entry too.

Safety guarantee — why committed entries are never lost

Raft's election restriction ensures a candidate can only win if its log is at least as up-to-date as a majority of the cluster. Because a committed entry is held by a majority, any future leader must have seen it — committed entries are never overwritten.

# Log completeness property (§5.4)
# If an entry is committed at term T:
#   - A majority of nodes hold it
#   - Any candidate winning an election has a log ≥ that majority
#   → future leader has the entry ✓

# "Up-to-date" comparison (last log entry):
#   if terms differ: higher term wins
#   if terms equal:  longer log wins

This is why Paxos is harder to understand: Paxos can elect a leader that doesn't have all committed entries and must learn them via a separate phase. Raft folds that learning into the election restriction itself.

Raft's main advantage is its deliberate decomposition and sequential log — no holes, no complex gap-filling logic. The tradeoff is that it is slightly less write-optimal than some Paxos variants that allow out-of-order commits.
