How does aw-sync work?

TL;DR: aw-sync pulls activity buckets from remote ActivityWatch instances and merges them into the local database. It tracks a cursor per peer to resume incrementally, skips version-incompatible peers gracefully, and reports every peer's outcome in a PeerReport.
Architecture overview

The sync runner discovers peers from ~/.config/activitywatch/aw-server/aw-server.toml (or the CLI --peers flag). For each peer it calls open_peer_datastores() then pull_from_remotes().

Cursor-based incremental sync

A cursor file stores the last-synced timestamp per (peer, bucket) pair. On each run, only events after the cursor are fetched — making syncs fast after the first full pull.

# Cursor file location (per-peer, per-bucket)
~/.local/share/activitywatch/aw-sync/
  cursors/
    192.168.1.10:5601/
      aw-watcher-window_hostname.cursor   # ISO timestamp
      aw-afk_hostname.cursor

If a cursor file is missing, aw-sync performs a full pull from the beginning of that bucket's history.

Peer compatibility & PeerReport

Before syncing, aw-sync checks the remote's API version. If the version is incompatible the peer is skipped (not fatal). Either way, a PeerReport entry is written so callers can surface the outcome.

OutcomePeerReport fieldMeaning
SuccesssucceededAll buckets pulled cleanly
Version mismatchskippedBenign; peer not compatible
Network errorfailedConnection refused / timeout

The record_peers flag must be true when calling pull_from_remotes to populate these fields — without it, failed/skipped peers are silently ignored (see issue #688).

Running aw-sync 
# Install (comes with ActivityWatch >= 0.13)
# Run a one-shot sync against a remote at 192.168.1.10
aw-sync --host 192.168.1.10:5601

# Continuous mode (re-syncs every N minutes)
aw-sync --host 192.168.1.10:5601 --interval 5

# Dry-run: show what would be synced without writing
aw-sync --host 192.168.1.10:5601 --dry-run
